# 10 — Bastion Host for Secure SSH Access

> The full stack from lesson 09, plus a bastion host and a real
> Terraform-generated SSH key pair — proving SSH-via-bastion and SSM
> coexist as two independent access paths, neither replacing the other.

## 1. Why a bastion, when SSM already works

Every lesson since 05 has used AWS Systems Manager (`aws ssm send-command`/
`start-session`) for instance access with **zero inbound security group
rules** — no port 22 anywhere. That's genuinely sufficient for automation
and scripted debugging, which is why `three-tier-deployment`'s entire Part
5/6 stayed "pure SSM, no bastion."

A bastion host adds something SSM doesn't: a normal `ssh` session — the
tool most engineers already know, usable with any SSH-aware tool (SCP,
`rsync`, an IDE's remote-SSH extension), not just the AWS CLI. This lesson
adds it **alongside** SSM, not instead of it — both are verified working
independently at the end.

## 2. A real Terraform-generated key pair

Every lesson so far avoided needing SSH entirely. This one needs a real key
pair, and it's generated by Terraform itself — not something a student
creates by hand in the AWS Console first:

```hcl
resource "tls_private_key" "bastion" {
  algorithm = "RSA"
  rsa_bits  = 4096
}

resource "aws_key_pair" "bastion" {
  key_name   = "three-tier-terraform-10-bastion"
  public_key = tls_private_key.bastion.public_key_openssh
}

resource "local_file" "private_key" {
  filename        = "${path.module}/three-tier-terraform-10-bastion.pem"
  content         = tls_private_key.bastion.private_key_pem
  file_permission = "0600"
}
```

The private key lands in a local `.pem` file (gitignored — `*.pem` in the
root `.gitignore`), never in a Terraform output, never committed. All
three instances (bastion, frontend, backend) share this one key pair — a
deliberate simplification for a teaching lab; a real fleet would likely use
per-role keys or, more commonly, skip long-lived keys entirely in favor of
`aws ec2-instance-connect` or SSM.

## 3. The chain, finally wired in for real

Lesson 07's `modules/security-group` chain (alb → frontend → backend → db,
plus the bastion group) gets used in a real deployment for the first time
here:

```hcl
module "sg" {
  source     = "./modules/security-group"
  vpc_id     = module.vpc.vpc_id
  my_ip_cidr = var.my_ip_cidr
}
```

## 4. A real bug this lesson surfaced: `count` on an unknown value

First `plan` failed:

```console
Error: Invalid count argument

  on modules\security-group\main.tf line 9, in data "aws_vpc" "default":
   9:   count   = var.vpc_id == null ? 1 : 0

The "count" value depends on resource attributes that cannot be determined
until apply, so Terraform cannot predict how many instances will be created.
```

`modules/security-group`'s `vpc_id` variable used to default to `null` and
fall back to a `count`-guarded default-VPC lookup *inside the module* —
fine when `vpc_id` is a literal `null` (lesson 07's standalone demo, where
it's known at plan time), but this lesson passes `module.vpc.vpc_id`, a
value that doesn't exist until the VPC is actually created. Terraform's
`count` meta-argument must be resolvable at plan time; it can't wait for an
apply-time value to find out whether the condition is true.

**Fix**: `vpc_id` became a required input with no module-side fallback;
lesson 07 now does its own default-VPC lookup in its own `main.tf` instead
(see [lesson 07's README](../07-security-groups-as-code/README.md#2-why-this-chain-doesnt-hit-the-destroy-order-bug-from-part-6)
for the full before/after). Moving a conditional lookup out of a shared
module and into whichever caller actually needs the fallback is generally
the safer pattern — it keeps the module's required inputs honest instead
of hiding a plan-time constraint inside a `count` expression.

### Proof: SSH reaches instances that have no public IP at all

Direct SSH to the bastion first:

```console
$ ssh -i three-tier-terraform-10-bastion.pem ubuntu@13.228.78.138 "hostname && whoami"
ip-10-0-0-92
ubuntu
```

Then `ProxyJump` through it to the **private** frontend — this is the
actual point of the lesson:

```console
$ ssh -i three-tier-terraform-10-bastion.pem \
    -J ubuntu@13.228.78.138 ubuntu@10.0.11.194 "curl -s localhost/health"
{"status":"ok"}
```

> **Note on `-J` and identity files**: on this machine's OpenSSH build,
> `-J user@jump` did not automatically reuse the `-i` key for the jump
> hop itself — it authenticated fine to the final target but failed with
> `Permission denied (publickey)` against the bastion. The reliable
> fix, if you hit the same thing, is an explicit `ProxyCommand` that
> passes the key to both hops:
> ```bash
> ssh -i key.pem \
>   -o "ProxyCommand=ssh -i key.pem -W %h:%p ubuntu@<bastion-ip>" \
>   ubuntu@<private-ip> "command"
> ```
> Whether `-J` alone works for you depends on your OpenSSH version and
> `~/.ssh/config` — if it works directly, use it; the `ProxyCommand` form
> above is the fallback that works everywhere.

And the backend, also private, also reachable only through the bastion:

```console
$ ssh -i three-tier-terraform-10-bastion.pem \
    -o "ProxyCommand=ssh -i three-tier-terraform-10-bastion.pem -W %h:%p ubuntu@13.228.78.138" \
    ubuntu@10.0.10.227 "curl -s localhost:3000/health && hostname"
{"status":"ok"}
ip-10-0-10-227
```

### Proof: SSM still works, independently, at the same time

```console
$ aws ssm send-command --instance-ids i-0d8b78a4cc1e14705 \
    --document-name AWS-RunShellScript --parameters commands='["hostname","whoami"]'
...
$ aws ssm get-command-invocation --command-id ... --instance-id i-0d8b78a4cc1e14705
Status: Success
Output: ip-10-0-11-194
        root
```

Both access paths work on the same instance at the same time — SSH via the
bastion authenticates as `ubuntu` with a key pair; SSM runs as `root`
through AWS's own control plane, no key or open port involved. Neither
depends on the other.

## If it breaks

- `Permission denied (publickey)` on the jump hop specifically (not the
  final target) — see the `-J` note above; use the explicit `ProxyCommand`
  form.
- `UNPROTECTED PRIVATE KEY FILE` warnings — the generated `.pem` gets
  `0600` from Terraform's `file_permission`, but some filesystems (notably
  Windows/NTFS under git-bash) don't map that reliably; run
  `chmod 600 three-tier-terraform-10-bastion.pem` before using it if `ssh`
  complains.
- `Invalid count argument` on `modules/security-group` — see §4; make sure
  you're on the fixed module version (`vpc_id` required, no module-side
  default-VPC fallback).
